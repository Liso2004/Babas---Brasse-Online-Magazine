# Baba's Brasse Online Magazine

Baba's Brasse is a React and Node.js online magazine for South African arts, literature, photography, profiles, reader responses, and editorial administration.

The repository is split into two runnable apps:

- `apps/web` - the React/Vite frontend.
- `apps/api` - the Node.js API, admin authentication, submission storage, and production static-file server.

The frontend can run by itself in Vite for design and route work. For real form submissions, admin inboxes, and persisted editorial content, run the API as well.

Important files:

- `apps/web/src/App.jsx` fetches published content from `/api/content` and falls back to launch fixtures if the API is unavailable.

## Frontend App

The frontend is a Vite app in `apps/web`.

Public pages include:

- `/` - homepage with featured editorial content, categories, media, and profiles.
- `/about` - magazine mission, editorial pillars, workflow context, and links into submissions.
- `/photography` and `/featured` - media/photography gallery pages.
- `/visceral-mag` - article archive.
- `/visceral-mag/:slug` - article detail pages with reader comments.
- `/people/:slug` - contributor or creative-team profile pages.
- `/contact` - public contact/submission form.

Admin and support pages include:

- `/admin/login` - administrator sign-in.
- `/admin` - admin dashboard.
- `/admin/articles` - article management.
- `/admin/profiles-media` - profile and media management.
- `/admin/moderation` - comment/review moderation.
- `/admin/contact-submissions` - contact form inbox.
- `/404`, `/500`, and `/offline` - support states.

## Fresh Clone Setup

A clone intentionally does not include `.env`, `node_modules`, `apps/web/dist`, or local submission data. Nothing in the repository should point to the original developer's computer.

From the cloned repository root:

```powershell
npm.cmd install
npm.cmd --prefix apps/web install
npm.cmd run setup:check
```

For public development, no `.env` file is required. To use the local admin login, create a machine-local file:

```powershell
Copy-Item .env.development.example .env
```

Then change `BABAS_ADMIN_EMAIL` and `BABAS_ADMIN_PASSWORD` in `.env`. The file is ignored by Git.

`npm.cmd run dev:api` always forces development mode and ignores `BABAS_WEB_DIST_PATH`. This prevents a global `NODE_ENV=production` or an absolute path from another computer from breaking local development.
### Run The Frontend Locally

Install dependencies once:

```powershell
npm.cmd install
npm.cmd --prefix apps/web install
```

Start the API in one terminal when you need live API data or form submissions:

```powershell
npm.cmd run dev:api
```

Start Vite in another terminal:

```powershell
npm.cmd run dev:web
```

The frontend runs at `http://127.0.0.1:5173`. Vite proxies `/api` to `http://127.0.0.1:8787`.

### Build The Frontend

```powershell
npm.cmd run build:production
```

This writes the static build to `apps/web/dist`.

## Backend / API App

The backend is a dependency-light Node.js HTTP server in `apps/api`.

It provides:

- `GET /api/health`
- `GET /api/content`
- `POST /api/contact-submissions`
- `POST /api/articles/:slug/comments`
- `POST /api/articles/:slug/reviews`
- Admin login/session/logout endpoints
- Admin content, moderation, and contact-submission endpoints

Run it locally from the repository root:

```powershell
npm.cmd run dev:api
```

By default it listens at `http://127.0.0.1:8787`.

In local development, data is stored in `apps/api/data/submissions.json` unless `BABAS_API_DATA_PATH` is set.

## Environment Variables

The API loads `.env` from the repository root when shell variables are not already set.

Required in production:

- `NODE_ENV=production`
- `PORT` - server port, usually provided by the host.
- `HOST` - bind host, often `0.0.0.0` in production.
- `BABAS_ADMIN_EMAIL` - administrator login email.
- `BABAS_ADMIN_PASSWORD_HASH` - scrypt hash generated by `npm.cmd run hash:admin-password`.
- `DATABASE_URL` - PostgreSQL connection string.

Optional / deployment-specific:

- `BABAS_DATABASE_SSL` - defaults to SSL enabled unless set to `0`.
- `BABAS_DATABASE_SSL_REJECT_UNAUTHORIZED` - defaults to certificate verification enabled unless set to `0`.
- `BABAS_ADMIN_TOKEN` - optional bearer token for trusted server automation.
- `BABAS_WEB_DIST_PATH` - only needed if the built frontend is not in `apps/web/dist`.
- `BABAS_LOGIN_RATE_LIMIT` - admin login attempts per window, default `5`.
- `BABAS_PUBLIC_RATE_LIMIT` - public submissions per window, default `20`.
- `BABAS_RATE_WINDOW_MS` - rate-limit window, default `900000`.
- `BABAS_TRUST_PROXY` - set to `1` only behind a trusted proxy that owns `X-Forwarded-For`.
- `BABAS_API_DATA_PATH` - local-development JSON storage override; production uses PostgreSQL.
- `BABAS_PUBLIC_SITE_URL` - canonical public origin used by the dynamic sitemap.

Frontend-only tooling variables:

- `WEB_BASE_URL` - used by route smoke and screenshot QA scripts to target a running site.
- `CHROME_BIN` - optional path for browser QA scripts.

No `VITE_*` runtime variables are currently required by the frontend.

## Admin / Editorial Workflow

The admin area is protected by server-side admin authentication.

In local development, set either:

- `BABAS_ADMIN_EMAIL` and `BABAS_ADMIN_PASSWORD`, or
- `BABAS_ADMIN_EMAIL` and `BABAS_ADMIN_PASSWORD_HASH`.

In production, plain `BABAS_ADMIN_PASSWORD` is rejected. Generate a hash with:

```powershell
$env:BABAS_ADMIN_PASSWORD_INPUT='<use-a-long-unique-password>'
npm.cmd run hash:admin-password
Remove-Item Env:BABAS_ADMIN_PASSWORD_INPUT
```

The editorial flow is:

1. Public pages load published content through `GET /api/content`.
2. Admin users sign in at `/admin/login`.
3. Admin pages create/update articles, profiles, media, moderation status, and contact submission status through `/api/admin/*`.
4. Production persists the publication state in PostgreSQL as JSONB.
5. Local development persists the same model to a JSON file.

## Form Submission Workflow

The contact form is connected end-to-end.

1. `apps/web/src/pages/ContactPage.jsx` handles the form submit.
2. It validates name, email, subject, message, and a hidden honeypot field.
3. `apps/web/src/forms/publicFormClient.js` posts JSON to `POST /api/contact-submissions`.
4. `apps/api/server.js` rate-limits public submissions and routes the request.
5. `apps/api/submissionStore.js` validates and stores the submission with status `new`.
6. Local development writes to `apps/api/data/submissions.json`.
7. Production writes to PostgreSQL through `apps/api/postgresSubmissionStore.js`.
8. Admin users review the inbox at `/admin/contact-submissions`.
9. The admin inbox can mark submissions `read` or `archived` via `PATCH /api/admin/contact-submissions/:id`.

The current system stores submissions for admin review. It does not send notification emails yet.

## Deployment

This repository currently assumes a single Node deployment that serves both the API and the built React app on one origin.

Deployment steps:

```powershell
npm.cmd install
npm.cmd --prefix apps/web install
npm.cmd run build:production
npm.cmd run db:migrate
npm.cmd run start:production
```

Production requirements:

- Node.js runtime capable of running `node apps/api/server.js`.
- PostgreSQL database reachable by `DATABASE_URL`.
- Production environment variables from `.env.production.example`.
- Built frontend at `apps/web/dist`, unless `BABAS_WEB_DIST_PATH` points elsewhere.

The API startup fails closed in production if required admin/database variables are missing or if the frontend build cannot be found.

## Checks

Useful checks from the repository root:

```powershell
npm.cmd test
npm.cmd run test:api
npm.cmd run verify:production
```

`npm.cmd test` builds the frontend and runs the route smoke check.

`npm.cmd run test:api` checks content delivery, contact validation and persistence, admin login, and the contact inbox using an isolated in-memory store.

`npm.cmd run verify:production` runs both checks.
